# 8.11 作业：按键状态机手搓代码心得

## 一、作业内容

这次作业是在 STM32F405 工程的 `main.c` 中，不直接调用已经封装好的 `state_machine_run()`，而是在 `while (1)` 中自己完成以下功能：

- 识别按键的短按和长按；
- 长按进入流水灯状态；
- 短按在流水灯和呼吸灯之间切换；
- 状态切换时让蜂鸣器响一次；
- 四盏 LED 依次形成流水灯效果；
- 四盏 LED 同时产生呼吸灯效果；
- 待机时关闭所有 LED。

## 二、手写过程中的理解

### 1. 按键电平和按键事件不是一回事

刚开始我容易把“按键现在被按下”直接理解成长按。后来我明白，按键电平只表示这一时刻按键是否按下，而短按、长按属于一段时间内发生的事件。

程序需要同时保存当前和上一轮的按键状态：

```c
uint8_t key_now;
uint8_t key_last;
```

当 `key_now == 1U`、`key_last == 0U` 时，说明按键刚刚按下；当 `key_now == 0U`、`key_last == 1U` 时，说明按键刚刚松开。

每轮循环最后都要执行：

```c
key_last = key_now;
```

如果忘记这一步，程序就无法比较前后两次电平，也会不断把持续按下误认为刚刚按下。

### 2. `uwTick` 用来计算经过的时间

`uwTick` 由 HAL 库维护，通常每 1 ms 增加一次。它记录的是系统启动后累计经过的毫秒数，不是一个动作的持续时间。

按键刚按下时保存时间：

```c
press_tick = uwTick;
```

之后通过相减计算按住了多久：

```c
uwTick - press_tick
```

当时间差达到 `1000U`，并且按键仍然按着，就可以判定为长按。

流水灯的 300 ms 切换和呼吸亮度的 10 ms变化也使用了同样的方法。这让我理解了非阻塞计时的基本写法：不是让程序停下来等待，而是让主循环继续运行，并不断检查时间是否到达。

### 3. `long_sent` 防止长按被重复触发

主循环运行速度很快。按键超过 1 秒以后，长按条件会在很多轮循环中持续成立。如果没有标志变量，蜂鸣器和状态切换就会被反复执行。

`long_sent` 的含义是“本次按住过程是否已经报告过长按”：

```text
0：还没有处理长按
1：长按已经处理
```

新一次按下时将它清零，识别到长按后将它置一。松开时还可以利用它判断这次操作是不是短按：如果松开时 `long_sent` 仍为零，说明按键没有按满 1 秒。

### 4. 状态变量是程序的记忆

这次使用 `current_state` 保存系统当前处于哪一种工作模式：

```text
0：待机
1：流水灯
2：呼吸灯
```

按键判断负责改变状态，后面的状态判断负责运行相应灯效。这两部分不能混为一个简单的 `if...else`。

我对主循环结构的理解变成了：

```text
读取按键
→ 识别短按或长按
→ 根据事件修改状态
→ 根据当前状态运行灯效
→ 保存本轮按键电平
```

蜂鸣器也应放在状态切换的位置，而不是放在某个状态的持续运行区。如果放在流水灯或呼吸灯状态内部，主循环每运行一轮都会响一次。

### 5. `uint8_t` 和 `uint32_t` 要根据用途选择

我一开始把时间变量和 LED 编号的类型写反了。后来总结出一个简单规律：

```text
状态、编号、真假标志 → uint8_t
系统时间和 tick      → uint32_t
需要保存负数的方向   → int8_t
```

例如：

```c
uint8_t current_led = 1U;
uint32_t last_led_time = 0U;
int8_t breath_direction = 1;
```

`current_led` 只需要保存 1～4；时间变量需要和 32 位的 `uwTick` 配合；呼吸方向需要保存 `1` 和 `-1`，所以不能使用无符号类型。

整数后面的 `U` 表示该常量是无符号整数，例如 `1000U`。它的数值仍然是 1000，但类型和 `uint32_t` 等无符号变量更加一致。

### 6. 流水灯不是只负责点亮下一盏灯

流水灯每 300 ms 执行一次切换，使用 `current_led` 记录当前要点亮的灯。

我原来以为 LED 初始全灭，所以只需要依次点亮即可。实际上初始全灭只发生一次，已经点亮的 LED 不会自动熄灭。如果一直只执行点亮操作，最后四盏灯会全部亮起。

因此每次切换的顺序是：

```text
先关闭四盏灯
→ 根据 current_led 点亮一盏
→ current_led 加一
→ 超过 4 后回到 1
```

其中 `last_led_time = uwTick;` 只是记录本次切换时间，并不会控制 LED。真正控制引脚的是 `GPIOA->BSRR`。

### 7. 呼吸灯由亮度变化和 PWM 两部分组成

呼吸灯不是简单地让一个变量从 0 加到 100。它包含两个不同速度的过程：

1. 每 10 ms 改变一次目标亮度，让 `breath_level` 在 0～100 之间往返变化；
2. 软件 PWM 快速比较 `pwm_count` 和 `breath_level`，决定四盏灯当前是亮还是灭。

例如 `breath_level` 等于 30 时，一个包含 100 个计数的 PWM 周期中，前 30 个计数亮、后 70 个计数灭。由于开关速度很快，人眼看到的是大约 30% 的平均亮度。

`breath_direction` 用来记录当前正在变亮还是变暗：到达 100 后改为 `-1`，到达 0 后恢复为 `1`。

## 三、遇到的问题

这次手写过程中，我遇到了以下容易犯的错误：

- 把按位与 `&` 写成逻辑与 `&&`；
- 把比较运算 `==` 写成赋值运算 `=`；
- 把只执行一次的按键检测写在 `while (1)` 外面；
- 忘记更新 `key_last`，导致长按起始时间不断刷新；
- 使用 `uint8_t` 保存系统时间；
- 把蜂鸣器调用写在状态运行区，导致蜂鸣器连续鸣叫；
- 流水灯只点亮新灯，没有关闭上一盏灯；
- `current_led` 加到 5 后没有重新回到 1；
- 复制呼吸灯代码时产生了重复的 `else` 和错误的花括号层级；
- 把低速亮度变化和高速 PWM 计数错误地放在同一个时间判断中。

这些问题让我认识到，写嵌入式程序不仅要关注某一行代码是否正确，还要注意它位于主循环的哪个层级、执行一次还是重复执行，以及是否会阻塞其他任务。

## 四、本次收获

这次作业最大的收获不是得到一份完整代码，而是理解了代码为什么要这样组织。

我学会了使用前后两次电平识别按下沿和松开沿，使用 `uwTick` 进行非阻塞计时，使用标志位避免事件重复处理，也理解了状态机中“事件改变状态、状态决定行为”的基本关系。

流水灯让我理解了顺序控制和循环编号，呼吸灯让我第一次把目标亮度、占空比和软件 PWM 联系起来。手动整理错误的花括号虽然比较累，但也让我意识到代码缩进和结构清晰非常重要。

后续如果继续完善，我希望将状态数字改成枚举，给按键增加更可靠的消抖处理，并使用定时器中断产生稳定的软件 PWM 节拍，减少主循环速度和阻塞式蜂鸣器对呼吸效果的影响。
